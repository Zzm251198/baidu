# 演示脚本与答辩口径

> 本文件所有数字均来自实测或测试断言（见每节末尾的"证据"）。
> 现场若被追问，能直接说出"这个数我在哪儿看过"。
> 2026-11 口径：全网纯地铁 16 条线建模（云巴/城际/有轨不纳入），492 单。

---

## 0. 一句话定位

**把地铁当成货运网络**：用真实深圳地铁线网做"时刻 + 车辆"的编排仿真，
回答"这一票货从 A 到 B，几趟车、几台 AGV、赚多少、风险在哪"，
并把答案做到**可复现、可审计、可对比**。

## 1. 十分钟演示脚本

### 第 1 站：实时监控（约 2.5 分钟）

| 动作 | 你要说的话 | 屏幕上会看到 |
|---|---|---|
| 打开首页 | "这是全网运营总览，仪表盘纵向流：首屏 KPI + 全宽地图" | KPI 一行四卡 + 1884px 全宽地图 |
| 指着四张卡 | "186 辆在任务 / 248 台在线 / 492 条运单 / 16 条线 / 平均 36 分钟 / 13 个异常" | 四卡数字 |
| 指地图 | "真实深圳底图 + 真实走位的 16 条线网，352 个站点圆点" | 彩色线网铺在真实街道上 |
| 指 ▲ 三角形 | "82 个真实物流仓库（物流园/分拨中心/货运站），POI 检索烘焙" | 琥珀色三角形 + 左下角图例 |
| 点「松岗」站 | "9 辆驻站小车，三电量段分组；松岗是双因子配比的榜首" | 站点弹窗：货运态势 + 该站小车 |
| 点右上「实时路况」 | "运输路线规划可以叠加实时路况" | 道路红黄绿流量 |
| 下滚到底部三面板 | "异常监控是**规则引擎实时算的**" | 5 条负载告警 + 5 条低电告警 |
| 展开车队电量窗口 | "248 辆按站点分组全览" | 全车队明细弹层 |

**要点**：
- `186 ≠ 248`。186 是"执行任务中"，248 是"在线设备总数"。
- **车队不是堆在大站**：按「物流中心邻近度 + 站点货运量」双因子配比到 61 个部署点
  （松岗 9 辆居首——物流园聚集区 + 自身有货量；CBD 站无仓库无货量，自然不配车）。
- **告警是算出来的**：站点负载率（积压指数）≥80% 告警、低电小车占比 >60% 告警，
  由运单聚合与车队明细实时推导，不是写死的示例。

### 第 2 站：货运数据（约 1.5 分钟）

| 动作 | 你要说的话 |
|---|---|
| 先看"命中 492 条运单" | "全量 492 单 = 16 条线 × 前 8 站 × 4 个月" |
| 线路选「地铁1号线」 | "492 → 32：8 个站 × 4 个月" |
| 品类选「生鲜食品」 | "32 → 6" |
| 月份选「2024年3月」 | "6 → 2。五个筛选器是 AND 语义" |

**要点**：如果现场被问"为什么罗湖不能选"——**数据只覆盖每条线前 8 站，罗湖是 1 号线第 30 站**。
这是有意的数据量控制，不是 bug。

### 第 3 站：单方案仿真 + 导出（约 3 分钟）

1. 起点 `11 号线 / 前海湾`，终点 `11 号线 / 岗厦北`，货运重量 `1200`
2. 路径策略选 **「均衡（换乘算 3 站）」**（不依赖百度可用性，稳）
3. 点「开始仿真」

| 你会看到 | 说法 |
|---|---|
| 效益看板：时长 / 站数 / 换乘 / 利润 | "一次仿真把一个订单的全链路算完" |
| AGV 编排 | "3 个作业节点？8 站直达是 2 个节点；换乘 1 次才是 3 个" |
| 点「导出 Excel」 | "导出的是 5 个 sheet：摘要 / 列车 / AGV / 作业 / 风险" |
| 打开表格指「调度算法 / 路径策略」两行 | "**导出的东西能自证是哪套算法跑出来的**" |

**基准数字（牛湖→公明广场，27 站 / 72 分 / 1 换乘 / 1200kg）**：
收入 **603.00** / 成本 **125.10** / 利润 **477.90**，前后端逐位一致。

### 第 4 站：多方案对比（约 2.5 分钟）★ 最值得讲

1. 起点 `2 号线 / 赤湾`，终点 `5 号线 / 布吉`，重量 `1200`
2. 点「多方案对比（路径 × 派车）」

| 方案 | 时长 | 换乘 | 利润 | 运力冗余 | 推荐 |
|---|---|---|---|---|---|
| 均衡 + 就近匹配 | 53 分 | 2 | ¥445.95 | 2236 kg | |
| 均衡 + 大运力优先 | 53 分 | 2 | ¥445.95 | **2757 kg** | ★ |
| 少换乘 + 就近匹配 | 73 分 | 0 | **¥490.75** | 590 kg | |
| 少换乘 + 大运力优先 | 73 分 | 0 | ¥490.75 | **786 kg** | ★ |

**四句话讲完这张表**：

1. **3 种路径策略 → 只有 2 条路**：均衡与时间优先同路，程序按路径签名去重了
2. **金额不随派车算法变**：钱只由「路径 + 订单」决定
3. **大运力优先优化的是运力冗余与电量稳健性**，不是账面数字
4. **推荐用帕累托前沿**：两个方案互不被全面压过，最终由人决策

**派车细节（被追问再讲）**：跨站调度有三级优先——枢纽池机动位 > 驻站不在本路线的车 > 顺序兜底。
盲取第一辆会抢走后续节点的本站待命车，这是代码评审抓出并修掉的真实缺陷（有回归测试）。

### 第 5 站：工程侧（约 1.5 分钟）

- **282 个自动化用例**：210 前端 + 53 后端 + 19 端到端
- **CI 三个 job**：类型+单测+打包 / pytest+口径自检 / 真实浏览器 E2E
- **一致性靠对拍**：同一组输入，JS 与 Python 必须都算出 603.00 / 125.10 / 477.90
- **离线也能用**：地图脚本挂了（无 AK / 离线）线网数据仍可用——烘焙进仓库，零运行时依赖

## 2. 五个可展开的技术点（每个：问题 → 做法 → 证据）

### 2.1 同一屏两个口径（早期真事故）

**问题**：卡片写"活跃小车 1,286 辆"，右侧面板写"在线设备 248 台"。
**做法**：车队单一下沉到 `public/data/agv_pool.json`，前端、后端、导出全读它。
**证据**：`tests/data/fleet.test.ts` 断言 `active+idle+charging === total`。

### 2.2 两套实现必须逐位一致（对拍）

**问题**：计费逻辑前端 JS、后端 Python 各一份，改一边没人发现。
**做法**：同一输入喂两边，硬性要求收入/成本/利润相同。
**证据**：`backend/tests/test_algorithm_switch.py`、`tests/simulation/metrics.test.ts`。

### 2.3 真实底图 + 烘焙线网（监控页地图）

**问题**：地铁图 SDK 只有抽象示意图，答辩讲不清"真实网络"。
**做法**：底图换百度地图 JS API（真实街道瓦片）；线网数据从百度线网接口**烘焙进仓库**
（每站真实墨卡托坐标 + 官方线色），运行时零网络依赖；82 个物流仓库 POI 同法烘焙。
**证据**：E2E 离线兜底用例——无 AK 时徽章与下拉照常（数据不依赖 SDK 加载）。

### 2.4 车队双因子配比 + 动态告警

**问题**：248 辆车堆在 9 个大站，中小货运站没车；告警是静态示例。
**做法**：配比 = 0.5×货运量归一 + 0.5×物流中心邻近度 e^(-d/3km)，取得分前 60 站部署
（保底 1 辆 + 加权分配）；告警由规则引擎实时推导（负载≥80%、低电占比>60%）。
**证据**：`src/analysis/dynamicAlerts.ts` + 5 例阈值边界单测；实机 5+5 条告警。

### 2.5 算法插点（可替换，不是硬编码）

- 插点 A（路径）：换乘惩罚 = 参数。`faster` 2 / `fewer` 8 / `balanced` 3。
- 插点 B（派车）：注册表一行登记一个算法；输出结构"只增不改"。
- 插点 C（车队数据）：`GET /api/fleet/vehicles` 是真实小车数据的接入窗口，
  未来换数据源接口不变。
- **证据**：新增算法只改注册表一行 + 一个 service 文件。

## 3. 答辩问答（按被问频率排序）

**Q1：数据是真的吗？**
A：**线网和仓库是真的**（16 条深圳地铁线 431 站次、82 个物流仓库 POI，坐标与线色来自百度开放数据）；
运单、车队、告警是**确定性生成**的演示数据。凡是生成数据，界面都标注口径。

**Q2：为什么 186 辆和 248 台不一样？**
A：248 = 在线设备总数；186 = 其中"执行任务中"。另有 37 待命、25 充电，三者相加 = 248。

**Q3：为什么批量运单是 492 条？**
A：每条线只取前 8 站。14 条线取满 8 站 + 6 号线支线 7 站 + 20 号线 4 站 = **123 站位** × 4 个月 = 492。

**Q4：为什么只有 16 条线？云巴、城际呢？**
A：建模口径主动收窄为**纯地铁骨干网**——云巴/有轨/城际制式不同、货运场景边缘，
纳入反而稀释口径。这是产品决策不是数据缺失，且全链路（徽章/下拉/聚合/后端自检）口径一致。

**Q5：收入 603 是怎么算的？**
A：基础票价 38 + 站数 27×5 + 重量 1200×0.35 + 换乘 1×10 = **603.00**。
成本 = 18 + 27×1.6 + 72×0.45 + 3 台 AGV×7.5 + 1×9 = **125.10**。利润 477.90。

**Q6：为什么同一路径下两种派车算法金额完全一样？**
A：收入/成本公式里**没有"派哪个车"这一项**——钱由路径与订单决定。
派车算法改变的是运力冗余与电量稳健性。

**Q7：为什么有些站显示"未部署小车"？**
A：车队按「物流中心邻近 + 货运量」双因子配比，只部署到得分的 61 个点。
CBD 站（如会展中心）附近无物流中心又无运单覆盖，模型判定不配车——
这正是配比模型**有区分度**的证据，不是遗漏。

**Q8：告警是实时的吗？**
A：规则引擎在前端实时推导（每次数据变化重算），数据来自后端运单聚合与车队明细接口。
阈值（80% / 60%）有单测锁边界。未来接真实车队数据后天然变成动态流。

**Q9：怎么保证前后端算出来一样？**
A：对拍测试。同一输入，JS 与 Python 必须同时等于 603.00 / 125.10 / 477.90；
任何一边改费率而另一边没跟上，CI 立刻红。

**Q10：为什么仿真要下沉到后端？**
A：**可审计**。每次运行落一条 `simulation_runs`（含算法与完整结果），可事后复盘。
另外后续接优化算法（OR-Tools）只换一个 service，接口不变。

**Q11：地图挂了还能用吗？**
A：能。线网数据烘焙在仓库里（不依赖地图脚本加载），徽章、下拉、聚合照常；
地图画布显示"底图暂不可用"提示条。E2E 有专门用例锁这个行为。

**Q12：有测试就够了吗？**
A：E2E 进 CI 第一次运行就抓出真实缺陷；代码评审还抓出"跨站调度劫持本站车"
的逻辑缺陷（已修 + 回归测试）。测试 + 评审两层都要。

**Q13：单文件分发版能跑吗？**
A：能。`npm run build` 产出 `dist/index.html`（**约 856 kB**，gzip 253 kB），JS/CSS 全内联。
地图底图需联网；没网时线网数据仍可用。

## 4. 已知局限（主动说，别等人问）

| 局限 | 说明 |
|---|---|
| 电量是静态快照 | 未接真实车队数据；`/api/fleet/vehicles` 接入窗口已留，接口不变 |
| 未建模站点的弹窗 | 显示示例值，界面已标注 |
| 路况默认关 | 与彩色线网叠加较花，演示时手动开 |
| AK 暴露在前端包内 | 上线必须配 Referer 白名单 |
| mock / http 吨位差约 1% | 生成器不同（mulberry32 vs Python random），条数/品类/月份完全一致 |
| 换乘惩罚未标定 | 3/8/2 是经验值 + 一个解析推导，没有用真实客流回归 |
| 告警阈值 80%/60% 未标定 | 业务经验值，规则与阈值已参数化可调 |

## 5. 上线清单（如果被问"明天能上吗"）

1. 配 AK 的 **Referer 白名单**；或把地图加载迁到后端代理
2. 设 `DEMO_ADMIN_TOKEN`，删掉"未配置即放行"的 demo 分支
3. CORS 收紧到实际域名
4. 数据库换 PostgreSQL（SQLite 单文件不适合并发写）
5. `/api/simulate` 加限流与鉴权；车队数据接真实网关（换 `load_agv_pool_agvs` 实现）
6. 告警阈值用真实业务数据标定
