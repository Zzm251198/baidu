# 演示脚本与答辩口径

> 本文件所有数字均来自实测或测试断言（见每节末尾的"证据"）。
> 现场若被追问，能直接说出"这个数我在哪儿看过"。

---

## 0. 一句话定位

**把地铁当成货运网络**：用真实深圳线网做"时刻 + 车辆"的编排仿真，
回答"这一票货从 A 到 B，几趟车、几台 AGV、赚多少、风险在哪"，
并把答案做到**可复现、可审计、可对比**。

## 1. 十分钟演示脚本

### 第 1 站：实时监控（约 1.5 分钟）

| 动作 | 你要说的话 | 屏幕上会看到 |
|---|---|---|
| 打开首页 | "这是全网的运营总览" | 1920×929 一屏，无滚动条 |
| 指着四张卡 | "186 辆在任务 / 248 台在线 / 620 条运单 / 20 条线 / 平均 36 分钟 / 3 个异常" | 四卡数字 |
| 点地图任意站点 | "站点维度也是同一份数据算的，不是另一套编的" | 左上弹出站点物流面板 |
| 指右下角标注 | "这是示意图，不是地理地图——地铁图 SDK 只给示意图" | 「示意图 · 非地理投影」 |

**要点**：`186 ≠ 248`。186 是"执行任务中"，248 是"在线设备总数"。
这两个数混在一起是这个项目早期真实踩过的坑，现在卡面副标题直接写开。

### 第 2 站：货运数据（约 1.5 分钟）

| 动作 | 你要说的话 |
|---|---|
| 先看"命中 620 条运单" | "全量 620 单 = 20 条线 × 前 8 站 × 4 个月" |
| 线路选「地铁1号线」 | "620 → 32：8 个站 × 4 个月" |
| 品类选「生鲜食品」 | "32 → 6" |
| 月份选「2024年3月」 | "6 → 2。五个筛选器是 AND 语义" |

**要点**：如果现场被问"为什么罗湖不能选"——**数据只覆盖每条线前 8 站，罗湖是 1 号线第 30 站**。
这是有意的数据量控制，不是 bug。

### 第 3 站：单方案仿真 + 导出（约 3 分钟）

1. 起点 `11 号线 / 前海湾`，终点 `11 号线 / 岗厦北`，货运重量 `1200`
2. 路径策略选 **「均衡（换乘算 3 站）」**（不依赖百度可用性，稳）
3. 点「开始仿真」

| 你会看到 | 说法 |
|---|---|
| 效益看板：时长 / 站数 / 换乘 / 利润 | "一次仿真把一个订单的全链路算完" |
| AGV 编排 | "3 个作业节点？这里 8 站直达是 2 个节点；换乘 1 次才是 3 个" |
| 点「导出 Excel」 | "导出的是 5 个 sheet：摘要 / 列车 / AGV / 作业 / 风险" |
| 打开表格指「调度算法 / 路径策略」两行 | "**导出的东西能自证是哪套算法跑出来的**" |

**基准数字（牛湖→罗湖，27 站 / 72 分 / 1 换乘 / 1200kg）**：
收入 **603.00** / 成本 **125.10** / 利润 **477.90**，前后端逐位一致。

### 第 4 站：多方案对比（约 2.5 分钟）★ 最值得讲

1. 起点 `2 号线 / 赤湾`，终点 `5 号线 / 布吉`，重量 `1200`
2. 点「多方案对比（路径 × 派车）」

| 方案 | 时长 | 换乘 | 利润 | 运力冗余 | 推荐 |
|---|---|---|---|---|---|
| 均衡 + 就近匹配 | 53 分 | 2 | ¥445.95 | 2236 kg | |
| 均衡 + 大运力优先 | 53 分 | 2 | ¥445.95 | **2757 kg** | ★ |
| 少换乘 + 就近匹配 | 73 分 | 0 | **¥490.75** | 590 kg | |
| 少换乘 + 大运力优先 | 73 分 | 0 | ¥490.75 | **786 kg** | ★ |

**四句话讲完这张表**：

1. **3 种路径策略 → 只有 2 条路**：均衡与时间优先同路，程序按路径签名去重了（否则表格里有两行一模一样）
2. **金额不随派车算法变**：同一路径下两行的收入/成本/利润完全相同——因为钱只由「路径 + 订单」决定
3. **大运力优先优化的是运力冗余与电量稳健性**，不是账面数字
4. **推荐用帕累托前沿，不是加权评分**：两个方案都没被任何方案全面压过（一个更快、一个更省装卸），所以都值得看，最终由人决策

### 第 5 站：工程侧（约 1.5 分钟）

- **263 个自动化用例**：195 前端 + 52 后端 + 16 端到端
- **CI 三个 job**：类型+单测+打包 / pytest+口径自检 / 真实浏览器 E2E
- **一致性靠对拍**：同一组输入，JS 与 Python 必须都算出 603.00 / 125.10 / 477.90
- **离线也能用**：地图 SDK 挂了（无 AK / 离线 / `file://`）仿真页仍可选线路

## 2. 五个可展开的技术点（每个：问题 → 做法 → 证据）

### 2.1 同一屏两个口径（早期真事故）

**问题**：卡片写"活跃小车 1,286 辆"，右侧面板写"在线设备 248 台"，同一屏两个数。
**做法**：车队单一下沉到 `public/data/agv_pool.json`，前端、后端、导出全读它；
`248/186/37/25` 各有测试盯着。
**证据**：`tests/data/fleet.test.ts` 断言 `active+idle+charging === total`。

### 2.2 两套实现必须逐位一致（对拍）

**问题**：计费逻辑前端一份 JS、后端一份 Python，改了一边没人发现。
**做法**：同一输入喂两边，硬性要求收入/成本/利润相同；连"金额口径不许随派车策略变"
也写成断言。
**证据**：`backend/tests/test_algorithm_switch.py`、`tests/simulation/metrics.test.ts`。

### 2.3 算法插点（可替换，不是硬编码）

- 插点 A（路径）：换乘惩罚 = 参数。`faster` 用 2，因为**换乘 5 分钟 ≈ 2 站 × 2.5 分钟**，等价于按时间最短；
  `fewer` 用 8（强偏直达）；`balanced` 用 3。
- 插点 B（派车）：注册表一行登记一个算法；输出结构"只增不改"，前端/导出/审计零改动即可消费。
- **证据**：新增算法只改 `ALGORITHMS` 一行 + 一个 service 文件。

### 2.4 多目标比较：为什么不用加权分

**问题**：想推荐"最优方案"，但时长/成本/换乘/冗余四个指标方向不同。
**做法**：帕累托前沿。只要没有方案在所有指标上都不差于它、且至少一项更好，它就在前沿上。
**证据**：`src/analysis/planCompare.ts` 的 `paretoFront` + 34 例单测（含"被全面压过的方案不在前沿"）。

### 2.5 测试分层（不是"为了覆盖率"）

| 层 | 抓什么 | 数量 |
|---|---|---|
| 纯函数单测 | 口径漂移、边界、去重、帕累托 | 195 |
| 后端接口 + 对拍 | 状态码、CRUD、金额一致 | 52 |
| E2E | 一屏布局、筛选联动、下载、离线兜底 | 16 |

**证据**：CI 三个 job；E2E 首次进 CI 就抓出"无 AK 时仿真页下拉为空"的真实缺陷。

## 3. 答辩问答（按被问频率排序）

**Q1：数据是真的吗？**
A：**线网是真的**（深圳地铁 20 条线 / 482 站），运单、车队、告警是**确定性生成**的演示数据
（同一份线网永远生成同一批，便于复现）。页面上凡是示例数据都标了「示例数据」。

**Q2：为什么 186 辆和 248 台不一样？**
A：248 = 在线设备总数；186 = 其中"执行任务中"。另有 37 待命、25 充电。三者相加 = 248。

**Q3：为什么批量运单是 620 条，不是 640？**
A：每条线只取前 8 站。20 号线只有 4 站、6 号线支线 7 站，所以是 18×8 + 7 + 4 = **155 站位** × 4 个月 = 620。

**Q4：收入 603 是怎么算的？**
A：基础票价 38 + 站数 27×5 + 重量 1200×0.35 + 换乘 1×10 = **603.00**。
成本 = 18 + 27×1.6 + 72×0.45 + 3 台 AGV×7.5 + 1×9 = **125.10**。利润 477.90。

**Q5：为什么同一路径下两种派车算法金额完全一样？**
A：因为收入/成本公式里**没有"派哪个车"这一项**——钱由路径（站数、换乘、时长）与订单（重量）决定。
派车算法改变的是"用哪些车、运力冗余多少、低电量车会不会出场"，那是稳健性，不是账面。

**Q6：既然金额一样，那"大运力优先"有什么用？**
A：同样的钱和时长下，**运力冗余更高**（赤湾→布吉：2757 kg vs 2236 kg），
意味着装货更从容、遇到大件不必换车；同时优先高电量车，**电量风险更低**。
这两点正是货运调度真正在意的。

**Q7：为什么推荐两个方案？不能给唯一答案吗？**
A：因为这是多目标问题：一条更快（53 分），一条更省装卸且更赚钱（0 换乘、利润多 44.80 元）。
"哪个更好"取决于业务偏好（时效 vs 装卸成本），**程序不该替业务拍板**。
加权评分可以给唯一解，但权重是主观的，评审一问"为什么时长占 40%"就答不上来。

**Q8：为什么"均衡"和"时间优先"给出同一条路？是 bug 吗？**
A：不是。两者惩罚是 3 和 2，在这条短程 OD 上不足以翻转选择（29 站直达 vs 17 站 2 换乘）。
差异出现在需要"少坐几站但多换一次"的边缘场景。这一点有测试固定（`routeStrategies.test.ts`），防止以后被误当 bug 改掉。

**Q9：换乘惩罚 3 / 8 / 2 是怎么定的？**
A：`faster` = 2 是**推导出来的**：换乘 5 分钟 ÷ 站间 2.5 分钟 = 2 站，所以惩罚 2 ≈ 按总时间最短。
`fewer` = 8、`balanced` = 3 是业务经验的保守取值（重柜怕装卸交接），属于可校准参数。

**Q10：怎么保证前后端算出来一样？**
A：对拍测试。同一组输入，前端 JS 与后端 Python 必须同时等于 603.00 / 125.10 / 477.90；
任何一边改费率而另一边没跟上，CI 立刻红。

**Q11：为什么仿真要下沉到后端？浏览器不能算吗？**
A：能算，但**不可审计**。下沉后每次运行落一条 `simulation_runs`（含请求与完整结果），
可以事后复盘"这条记录是怎么跑出来的"——现在连"用了哪种算法、哪条路径策略"都记了。
另外后续接优化算法（OR-Tools / 图算法）只换一个 service，接口不变。

**Q12：路径为什么还要留在前端？**
A：因为百度地铁库只能跑在浏览器（依赖浏览器环境），而且 AK 在前端包里。
所以分工是：**前端查路 → 后端编排与测算**。

**Q13：有测试就够了吗？怎么证明测试是有效的？**
A：这次 E2E 进 CI 第一次运行就红了 5 个——**抓出"没 AK 时仿真页不可用"的真实缺陷**，
而不是"测试都绿但线上崩"。反向证明：测试也确实抓到过我自己写错的断言（色标方向、终端行重复）。

**Q14：地图为什么没有街道底图？**
A：用的是百度**地铁图 SDK**（`type=subway`），它输出的是 SVG 示意图，本身不含瓦片底图——
实测抓包：页面只发了 5 个百度请求（SDK/校验/数据/版权图），**零瓦片请求**。
我们在此基础上叠了网格/暗角/「示意图 · 非地理投影」标注，并补充了"无 AK 时回退数据源线网"。

**Q15：单文件分发版能跑吗？**
A：能。`npm run build` 产出 `dist/index.html`（**751.03 kB**，gzip 219.84 kB），JS/CSS 全内联，双击即可打开。
注意：需要联网加载地图 SDK；**没网也没关系**——仿真页现在会回退到内置线网。

**Q16：为什么有 263 个测试却还是"演示数据"？**
A：测试保证的是**逻辑与口径**（同一输入同一输出、前后端一致、界面不塌），
不是"业务数据来自真实系统"。这两件事要分开讲，混在一起就是夸大。

## 4. 已知局限（主动说，别等人问）

| 局限 | 说明 |
|---|---|
| 未建模站点的弹窗 | 显示示例值，界面已标注「示例数据」 |
| 地图缩放 | 百度地铁图 SDK 无缩放 API，所以路线图做成"缩略图 + 分段行程列表" |
| AK 暴露在前端包内 | 上线必须配 Referer 白名单（否则配额会被盗刷） |
| mock / http 吨位差约 1% | 生成器不同（mulberry32 vs Python `random`），条数/品类/月份完全一致 |
| 管理接口 | 设 `DEMO_ADMIN_TOKEN` 后需带 `X-Demo-Token`；未设时本机放行（demo 模式） |
| 派车未建模距离 | 大运力优先忽略"车停在哪个站"，没有跨站调度的迁移成本 |
| 换乘惩罚未标定 | 3/8/2 是经验值 + 一个解析推导，没有用真实客流/装卸数据回归 |

## 5. 上线清单（如果被问"明天能上吗"）

1. 配 AK 的 **Referer 白名单**；或把查路迁到后端代理（AK 不进前端包）
2. 设 `DEMO_ADMIN_TOKEN`，删掉"未配置即放行"的 demo 分支
3. CORS 收紧到实际域名（现在是 localhost:3000）
4. 数据库换 PostgreSQL（SQLite 单文件不适合并发写）
5. 给 `/api/simulate` 加限流与鉴权
6. E2E 加一条"mock 模式"用例（现在 CI 只跑 http）
